# Milestone 2: asynchronous video API contract

This contract separates HTTP, storage, job persistence, and video processing. It is
provider-independent; the first adapter stores files and jobs locally.

## Endpoints

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/api/video-sessions` | Validate metadata, create a job, and return a short-lived upload target. |
| `PUT` | returned upload URL | Upload the video directly to storage. The production API server does not proxy video bytes. |
| `POST` | `/api/video-sessions/{id}/upload-complete` | Verify size/checksum, mark the upload complete, and enqueue processing. |
| `GET` | `/api/video-sessions/{id}` | Poll job status and obtain result URLs after completion. |

Request and response schemas live in `gymbromatics/upload_contract.py`. The routes
will be connected to FastAPI after the worker/enqueue boundary is introduced.

## State machine

```text
created -> uploaded -> queued -> processing -> complete
    |          |          |          |  |
    +----------+----------+----------+  +-> queued (retry)
                       any active state -> failed
```

`complete` and `failed` are terminal. Repeating the current state is idempotent.
Every persisted change increments `version`; repositories reject a stale version so
two workers cannot silently overwrite one another.

## Limits and trust boundaries

- Supported inputs: MP4, QuickTime/MOV, and WebM.
- Maximum declared video size: 250 MiB.
- The upload confirmation must match storage metadata and SHA-256 before queueing.
- Object keys are generated by the server. Original filenames are metadata only.
- The local adapter is for development. A cloud adapter can create signed upload
  URLs without changing the job model or processing worker.
