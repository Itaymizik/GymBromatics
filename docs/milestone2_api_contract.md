# Milestone 2: asynchronous video API contract

This contract separates HTTP, storage, job persistence, and video processing. It is
provider-independent; the first adapter stores files and jobs locally.

## Endpoints

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/api/video-sessions` | Validate metadata, create a job, and return a short-lived upload target. |
| `PUT` | returned upload URL | Upload the video directly to storage. The production API server does not proxy video bytes. |
| `POST` | `/api/video-sessions/{id}/upload-complete` | Verify size/checksum, mark the upload complete, and enqueue processing. |
| `GET` | `/api/video-sessions/{id}` | Poll job status and obtain result URLs after completion. |

Request and response schemas live in `gymbromatics/upload_contract.py`. The routes
are connected to FastAPI with local filesystem adapters. Upload confirmation moves
the job to `queued`; a later worker step will consume that state and run analysis.

## State machine

```text
created -> uploaded -> queued -> processing -> complete
    |          |          |          |  |
    +----------+----------+----------+  +-> queued (retry)
                       any active state -> failed
```

`complete` and `failed` are terminal. Repeating the current state is idempotent.
Every persisted change increments `version`; repositories reject a stale version so
two workers cannot silently overwrite one another.

## Limits and trust boundaries

- Supported inputs: MP4, QuickTime/MOV, and WebM.
- Maximum declared video size: 250 MiB.
- The upload confirmation must match storage metadata and SHA-256 before queueing.
- Object keys are generated by the server. Original filenames are metadata only.
- The local adapter is for development. A cloud adapter can create signed upload
  URLs without changing the job model or processing worker.

## Try the local flow from PowerShell

Start the API from the repository root:

```powershell
.\.venv\Scripts\python.exe -m uvicorn gymbromatics.api:app --host 127.0.0.1 --port 8765
```

In a second PowerShell window:

```powershell
$video = (Resolve-Path "data\squatsample.mp4").Path
$file = Get-Item -LiteralPath $video
$checksum = (Get-FileHash -LiteralPath $video -Algorithm SHA256).Hash.ToLowerInvariant()
$createBody = @{
    filename = $file.Name
    content_type = "video/mp4"
    size_bytes = $file.Length
    checksum_sha256 = $checksum
} | ConvertTo-Json

$created = Invoke-RestMethod `
    -Uri "http://127.0.0.1:8765/api/video-sessions" `
    -Method Post -ContentType "application/json" -Body $createBody

$receipt = Invoke-RestMethod `
    -Uri $created.upload.url -Method Put -InFile $video -ContentType "video/mp4"

$confirmBody = @{
    size_bytes = $receipt.size_bytes
    checksum_sha256 = $receipt.checksum_sha256
} | ConvertTo-Json

Invoke-RestMethod `
    -Uri "http://127.0.0.1:8765/api/video-sessions/$($created.session_id)/upload-complete" `
    -Method Post -ContentType "application/json" -Body $confirmBody

Invoke-RestMethod `
    -Uri "http://127.0.0.1:8765/api/video-sessions/$($created.session_id)"
```

After the upload reaches `queued`, run the local worker from another PowerShell
window:

```powershell
.\.venv\Scripts\python.exe -m gymbromatics.worker
```

The command processes all currently queued jobs and exits. To keep a development
worker running and polling for new uploads:

```powershell
.\.venv\Scripts\python.exe -m gymbromatics.worker --watch
```

Poll the status endpoint again after processing. A successful job returns
`complete` and four `result_urls`: the annotated MP4, raw analysis JSON, portable
dashboard HTML, and dashboard JSON. Failed jobs return a stable `error_code`
without exposing an internal stack trace through the API.

The local worker uses `.gymbromatics-local` for job records, objects, and temporary
work files. This directory is ignored by Git.
